## 3. แนวทางไม่ผูกผู้ให้บริการ (Portability)

| ส่วน | ใช้ | ย้ายผู้ให้บริการได้เพราะ |
|---|---|---|
| Compute | VM Linux ธรรมดา + Docker Compose | ไม่ใช้บริการ serverless/เฉพาะค่าย |
| Database | PostgreSQL 16 มาตรฐาน — Managed หรือติดตั้งเองก็ใช้โค้ดเดียวกัน ไม่ใช้ extension เฉพาะค่าย | `pg_dump` / `pg_restore` ย้ายได้ทุกที่; backup ภายนอกรายวันเป็นรูปแบบมาตรฐานเสมอ |
| ไฟล์แนบ | storage interface ในโค้ด: ดิสก์ในเครื่อง (เริ่มต้น) / S3 API | S3 API มีเกือบทุกผู้ให้บริการ |
| Backup | เก็บที่ผู้ให้บริการอีกราย | ถ้าผู้ให้บริการหลักมีปัญหา ข้อมูลยังอยู่ |
| โดเมน / DNS | อยู่กับผู้จดโดเมนของบริษัท | ย้ายเครื่อง = แก้ DNS record เดียว |
| การติดตั้ง | `deploy/provision.sh` + `docker-compose.yml` + คู่มือ | ติดตั้งเครื่องใหม่จากศูนย์ ~1 ชม. |
| การพิสูจน์ | ซ้อมย้ายปีละครั้ง: restore backup ภายนอกลง VM ของผู้ให้บริการอื่น + ชุดตรวจ | มีบันทึกผลซ้อม |

## 4. แนวทางขยายระบบ

ด้วยผู้ใช้ ≤ 10 คน คาดว่าจะอยู่ขั้นที่ 1 ได้หลายปี โครงสร้างรองรับขั้นถัดไปโดยไม่แก้โค้ด

| ขั้น | สัญญาณ | ทำอะไร | หยุดระบบ |
|---|---|---|---|
| 1 | เริ่มต้น | App VM 1 vCPU/2 GB + Managed PostgreSQL เล็กสุด | — |
| 2 | ผู้ใช้ > 15 หรือ CPU/RAM > 70% ต่อเนื่อง | ขยาย App VM เป็น 2 vCPU/4 GB และ/หรือ DB แพ็กเกจถัดไป (คลิกในหน้าจอผู้ให้บริการ) | ~5–10 นาที นอกเวลางาน |
| 3 | ต้องการไม่ให้ DB ล่มเมื่อเครื่องเสีย | เปิด standby node ของ Managed PostgreSQL (สลับอัตโนมัติ) | ไม่หยุด |
| 4 | ผู้ใช้ > 50 หรือเปิดสาขา | API 2 เครื่องหลัง Load balancer, ไฟล์แนบไป Object storage | ไม่หยุด (rolling) |
| 5 | รายงานหนัก/ข้อมูลหลายปี | Read replica สำหรับรายงาน, partition `audit_logs`/`stock_transactions` | ไม่หยุด |

(ถ้าเลือกแบบ A: ขั้น 3 คือย้าย DB ไป Managed ด้วย dump/restore ~30 นาที)

## 5. Backup & Restore ✅ (ข้อกำหนด: อัตโนมัติ + ไปอีกผู้ให้บริการ + ทดสอบ Restore)

| ชั้น | วิธี | ความถี่ / เก็บ | ผู้ดูแล |
|---|---|---|---|
| 1. Backup ของ Managed PostgreSQL | อัตโนมัติ + PITR 7 วัน (แบบ B) | ทุกวัน | ผู้ให้บริการ |
| 2. **Backup ภายนอก (บังคับ)** | `pg_dump -Fc` → เข้ารหัส (restic/age) → Object storage **ผู้ให้บริการอีกราย** | ทุกวัน 02:00 · 14 วัน + รายสัปดาห์ 8 + รายเดือน 12 | อัตโนมัติ (job ใน App VM) |
| 3. ไฟล์แนบ | sync เข้ารหัสไปที่เดียวกับชั้น 2 | ทุกวัน | อัตโนมัติ |
| 4. ก่อนเปลี่ยน schema / deploy | dump อัตโนมัติก่อน migration | เก็บ 30 วัน | อัตโนมัติ |
| 5. Snapshot App VM | บริการของผู้ให้บริการ | รายวัน 7 วัน | ผู้ให้บริการ |
| 6. 💡 สำเนาออฟไลน์ (แทน NAS) | ฮาร์ดดิสก์ภายนอก ดาวน์โหลด backup ที่เข้ารหัสแล้ว **เดือนละครั้ง** เก็บในตู้เซฟสำนักงาน (~2,000–3,000 บาท ครั้งเดียว) | รายเดือน | ผู้รับผิดชอบที่บริษัท (ทำตามคู่มือ 10 นาที) |

**ขั้นตอนทดสอบ Restore**
1. **อัตโนมัติรายสัปดาห์** (วันอาทิตย์): เปิด Staging → ดึง backup ภายนอกล่าสุด → ถอดรหัส → `pg_restore` → ตรวจจำนวนแถวทุกตาราง, ยอดลูกหนี้, ยอดเจ้าหนี้, มูลค่าสต๊อก เทียบค่าที่บันทึกตอน backup → ส่งผล ผ่าน/ไม่ผ่าน ทางอีเมลถึงผู้รับผิดชอบ (⏳ C-11) → ปิด Staging
2. **ซ้อมกู้เต็มรูปทุก 6 เดือน และก่อน go-live:** สร้าง VM ใหม่ + restore + เปลี่ยน DNS ชั่วคราว จับเวลาเทียบ RTO
3. **ซ้อมกู้แบบ PITR ปีละครั้ง** (แบบ B): กู้ DB ไปจุดเวลาที่กำหนด
4. บันทึกผลทุกครั้งใน `docs/DEVLOG.md` / รายงานผู้ดูแล

เป้าหมาย: **RPO ≤ 5 นาที (แบบ B ด้วย PITR) หรือ ≤ 24 ชม. (แบบ A) · RTO ≤ 2 ชม.**
กุญแจถอดรหัส backup เก็บ 2 ที่ (ผู้บริหาร + ตัวจัดการรหัสผ่าน/ซองปิดผนึกในตู้เซฟ) — กุญแจหาย = backup ใช้ไม่ได้

## 6. ความปลอดภัยบน Cloud

| ชั้น | มาตรการ |
|---|---|
| บัญชี Cloud | เปิดในนามบริษัท (⏳ C-9), 2FA บังคับทุกบัญชีผู้ดูแล, ผู้พัฒนาได้สิทธิ์แยกและถอนได้ |
| เครือข่าย | Firewall เปิดเฉพาะ 80/443 · SSH ด้วย key ผ่าน VPN ผู้ดูแลเท่านั้น · PostgreSQL รับการเชื่อมต่อเฉพาะจาก App VM (private network / IP allowlist + TLS) |
| เครื่อง | อัปเดตความปลอดภัยอัตโนมัติ, ไม่ใช้ root, fail2ban, เข้ารหัสดิสก์ตามที่ผู้ให้บริการรองรับ |
| แอป | HTTPS (Let's Encrypt อัตโนมัติ), HSTS, CSP, cookie Secure/HttpOnly/SameSite, CSRF, rate limit, ล็อกบัญชี, 💡 2FA (TOTP) Admin + ผู้อนุมัติ (C-6) |
| ข้อมูล | Backup เข้ารหัสก่อนออกจากเครื่อง, secrets ไม่เข้า git, DB user แยกสิทธิ์ |
| การเฝ้าระวัง | Uptime monitor ภายนอกทุก 1 นาที · แจ้งเตือน: ระบบล่ม, backup/restore test ล้มเหลว, ดิสก์ใกล้เต็ม, cert ใกล้หมดอายุ, login ผิดปกติ → ส่งถึงผู้รับผิดชอบ (⏳ C-11) |
| PDPA | Data Processing Agreement กับผู้ให้บริการ, บันทึกประเทศที่เก็บข้อมูล (⏳ C-2) |

## 8. Region และผู้ให้บริการ (⏳ C-2)

| Region | ความหน่วงจากนครปฐม | หมายเหตุ |
|---|---|---|
| Singapore | ~30–50 ms (ใช้งาน ERP ไม่รู้สึกช้า) | ทุกรายใหญ่มี, ราคาถูกกว่า, ข้อมูลอยู่นอกประเทศ |
| Thailand (Bangkok) | ~5–15 ms | มีทั้งรายต่างชาติที่เปิด region ไทยและรายในไทย, เหมาะถ้าลูกค้า/นโยบายกำหนดให้ข้อมูลอยู่ในไทย, ต้องตรวจว่ามี Managed PostgreSQL ใน region นั้นหรือไม่ |

เกณฑ์เลือกผู้ให้บริการหลัก: มี region ที่ต้องการ · มี **Managed PostgreSQL 16 + PITR** · snapshot + firewall + private network + 2FA · ขยายเครื่องได้ไม่ต้องย้าย · ออกใบกำกับภาษี/ใบเสร็จที่ฝ่ายบัญชีใช้ได้ · ชำระในนามบริษัทได้
ผู้ให้บริการ Object storage สำหรับ backup: **ต้องเป็นคนละรายกับผู้ให้บริการหลัก** และรองรับ S3 API

## 9. กรณีอินเทอร์เน็ตโรงงานขัดข้อง (ปรับตามข้อมูล: เน็ตแทบไม่ล่ม, ไม่มีเน็ตสำรอง)

เมื่อใช้ Cloud ระบบยังทำงานปกติ แต่ผู้ใช้ในโรงงานเข้าไม่ได้ระหว่างเน็ตล่ม (ผู้ใช้นอกโรงงานใช้ได้)

| ชั้น | มาตรการ |
|---|---|
| 💡 1. ระยะแรก: **ไม่ซื้อ Router 4G/5G** | เน็ตโรงงานแทบไม่ล่ม ความคุ้มค่ายังต่ำ |
| 💡 2. **แผนฉุกเฉินผ่าน Mobile Hotspot** | กำหนดล่วงหน้า **2 คน** (เช่นผู้บริหาร + หัวหน้าฝ่ายขาย/บัญชี) ที่มือถือมีแพ็กเกจเน็ตเพียงพอ เปิด Hotspot ให้เครื่องที่ต้องออกเอกสาร · ระบบใช้ข้อมูลน้อย (~50–150 MB/คน/วัน) · ทดสอบใช้งานผ่าน Hotspot จริงใน B3 · ติดคู่มือ 1 หน้า (ชื่อ Hotspot, ใครเปิด, งานที่ทำก่อน) ไว้ที่ฝ่ายขาย/บัญชี |
| 3. Downtime procedure (ถ้า Hotspot ใช้ไม่ได้) | (ก) ใช้ **ใบบันทึกชั่วคราว** (กระดาษ เลขเล่มของตัวเอง ไม่ใช่เลขเอกสารระบบ) สำหรับส่งของ/รับของ/ผลิต · (ข) เมื่อเน็ตกลับ คีย์เข้าระบบภายในวันเดียวกัน อ้างเลขใบชั่วคราวในช่องอ้างอิง · เลขจริงออกจากระบบเท่านั้น จึงไม่ชน (สอดคล้อง D-6) |
| 4. เกณฑ์ทบทวนการซื้อ Router | ถ้าเน็ตล่มกระทบงาน **มากกว่า 2 ครั้งต่อเดือน หรือครั้งละเกิน 1 ชม.** → เสนอซื้อเราเตอร์ Dual-WAN + 4G (~3,000–8,000 บาท + ซิม 300–600 บาท/เดือน) |
| 5. เฝ้าระวัง | Uptime monitor ภายนอกแยกได้ว่าปัญหาอยู่ที่ server (แจ้งผู้ดูแล) หรือที่เน็ตโรงงาน (server ปกติ) |

**ไม่ทำโหมดออฟไลน์ในเบราว์เซอร์** เพราะจะเกิดเลขเอกสารชน สต๊อกตัดซ้ำ และการอนุมัติที่ตรวจสิทธิ์ไม่ได้
