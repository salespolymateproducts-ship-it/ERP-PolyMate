# DEVLOG — PolyMate ERP

## 2026-11-17 · ระบบซื้อมาขายไปครบวงจร (ขั้น 1 + 2) ✅ (ทำบน localhost เท่านั้น ยังไม่ push / ไม่ deploy)
เดิม PO และการรับของรองรับเฉพาะวัตถุดิบ (ยิง PO ที่มีสินค้า FG-007 ได้ 400) สินค้าซื้อมาขายต้องรับด้วยการปรับสต๊อกมือ ไม่มีเจ้าหนี้/ต้นทุนจริง และต้นทุนขายคิดจากต้นทุนปัจจุบันย้อนหลัง — ผู้ใช้สั่งทำทั้งหมด (ช่วยงาน OEM ในอนาคตด้วย)

**ขั้น 1: ซื้อเข้า → รับของ → ต้นทุน**
- สินค้า "สั่งซื้อได้" = ประเภทซื้อมาขายไป หรือเปิดธง `buyable` (เช่น สินค้า OEM ที่จ้างผู้อื่นผลิต); ฟิลด์ใหม่ ผู้ขายประจำ, จุดสั่งซื้อ `min`, ระยะเวลาสั่งของ `leadDays`
- PO: บรรทัดมี `itemType` (material ค่าเริ่มต้น / product); server ตรวจสินค้า (ต้องมี/ซื้อได้/ไม่ปิดใช้งาน/ไม่ซ้ำ) กฎเดิมเหมือนวัตถุดิบ; ฟอร์ม PO เลือกจาก 2 กลุ่ม (วัตถุดิบ / สินค้าซื้อมาขาย) พร้อมประวัติราคาซื้อ
- `receivePO` รองรับบรรทัดสินค้า: เพิ่ม stock สินค้า + movement (ราคา/ต้นทุนก่อนหลัง) + ต้นทุนถัวเฉลี่ยเข้า `finished.cost` + ประวัติต้นทุน + เจ้าหนี้ (หมวดใหม่ "สินค้าซื้อมาขาย" ถ้าเป็นสินค้าล้วน) ใน transaction เดียว; บรรทัดจับคู่ไม่ได้ปฏิเสธทั้งใบ
- ต้นทุนสินค้าที่สั่งซื้อได้แก้ตรงไม่ได้ทุก role (409 `COST_MANAGED`); ปรับโดย admin ผ่าน `POST /actions/products/{id}/adjust-cost` พร้อมเหตุผล + ประวัติ + audit; ตอนสร้าง/เปิดธง ค่า cost ที่กรอกคือต้นทุนยกมา; สินค้าผลิตเอง (ไม่ซื้อได้) ใช้ต้นทุนมาตรฐานกรอกมือเหมือนเดิม
- หน้าสินค้า: ฟอร์มเพิ่ม/แก้มีผู้ขายประจำ/Min/วันสั่งของ/ธงสั่งซื้อได้, ต้นทุนเป็นค่าอ่านอย่างเดียวพร้อมปุ่ม admin ปรับ, ประวัติราคาซื้อและประวัติต้นทุน, ป้าย "ต่ำกว่า Min", ปุ่ม "สั่งซื้อ" (สร้าง PO รออนุมัติให้ผู้ขายประจำ ราคาตั้งต้น = ซื้อล่าสุด)
- **ต้นทุน ณ วันส่ง**: ใบส่งสินค้าบันทึก `unitCost` ไว้ที่รายการตอนอนุมัติ; ต้นทุนขายของใบกำกับภาษีคิดจากค่านี้ตามสายเอกสารต้นทาง (เอกสารเก่าที่ไม่มีค่านี้ใช้ต้นทุนปัจจุบัน)
- แจ้งเตือนสินค้าซื้อมาขายต่ำกว่า Min (บอกว่าสั่งซื้อแล้วหรือยัง)

**ขั้น 2: เชื่อมใบสั่งขาย**
- ความต้องการสินค้า = ที่เหลือส่งของใบสั่งขายที่อนุมัติแล้ว + ใบส่งสินค้าที่ยังไม่อนุมัติ; ขาด = ความต้องการรวม − สต๊อก − ที่สั่งซื้อไว้แล้ว (PO รออนุมัติ/อนุมัติแล้ว) แบบเดียวกับวัตถุดิบ ไม่มีลำดับก่อนหลัง
- ใบสั่งขายแสดงแถบสินค้าซื้อมาขายที่สต๊อกไม่พอ (ต้องส่ง/ทุกใบรวม/สต๊อก/สั่งไว้แล้ว/ขาด) พร้อมปุ่มสั่งซื้อ (จำนวนตั้งต้น = ยอดขาด); หลังสั่งแล้วเป็น "รอรับของ" ไม่สั่งซ้ำ; แจ้งเตือนใบสั่งขายรอสินค้า

**ผลทดสอบ:** gradlew test 63 เคสผ่าน (`TradeGoodsTests` 8 เคส) + บนหน้าเว็บจริง: ตั้งผู้ขาย/Min/7 วันให้ TR-GLOVE-NBR, ออก PO2026110009 (100 @110) ผ่านฟอร์ม → อนุมัติ → รับ: stock 480→580, ต้นทุน 95→97.5862, เจ้าหนี้หมวดสินค้าซื้อมาขาย; ใบสั่งขาย 400+300 vs stock 580 → ขายรวม 120, แถบเตือน, สั่งซื้อ PO2026110010 → "รอรับของ" ไม่สั่งซ้ำ; ส่ง DO 400 ชิ้น (unitCost 97.5862) แล้วรับ PO ใหม่ ต้นทุนขยับเป็น 102.5517 → ใบแจ้งหนี้ยังคิดต้นทุนขาย 39,034.48 (ไม่ใช่ 41,020.68); ฟอร์มเพิ่มสินค้าซื้อมาขายบังคับต้นทุนยกมาเมื่อมีสต็อกตั้งต้น
**ข้อจำกัด:** การตัดสต๊อกของใบส่งสินค้ายังทำฝั่งเบราว์เซอร์ (ซิงก์ทีละรายการ ไม่ใช่ transaction เดียว — Roadmap B3) ไม่ได้แก้ในรอบนี้; ต้นทุนขายย้อนหลังของใบส่งสินค้าเก่าก่อนวันนี้ใช้ต้นทุนปัจจุบัน; ใบสั่งซื้อที่รออนุมัติถูกนับเป็น "สั่งไว้แล้ว" ถ้ายกเลิกทีหลังยอดขายจะกลับมาเตือนเอง

## 2026-11-17 · จัดการเครื่องจักร + บำรุงรักษา + เตือนคู่เครื่อง/แม่พิมพ์ ✅ (ทำบน localhost เท่านั้น ยังไม่ push / ไม่ deploy)
เดิมเครื่องเป็นข้อมูลตัวอย่างในโค้ด ไม่มีหน้าเพิ่ม/แก้ — ผู้ใช้สั่ง: เพิ่มเครื่อง, ระยะห่างเสา/ช่วงความหนาแม่พิมพ์ ("ระยะแคมป์" = ช่วงความหนาแม่พิมพ์ที่เครื่องหนีบได้ ผู้ใช้ยืนยันแล้ว), ระบบบำรุงรักษา, สภาพเครื่องพร้อมเหตุผลที่ผู้ใช้กรอกเอง, เตือน (ไม่บล็อก ไม่ผูกคู่) เมื่อแม่พิมพ์ไม่เข้ากับเครื่อง

**สิ่งที่เปลี่ยน**
- Server (`MachineService` ใหม่ + `RecordService`): กฎเครื่อง — รหัสไม่ซ้ำ (ไม่สนตัวพิมพ์), ตัน > 0, ระยะห่างเสาต้องกรอกทั้งกว้าง/ยาว, ความหนาต่ำสุด ≤ สูงสุด, รอบ PM 1–3650 วัน (ตั้งต้น 90), ห้ามลบ; แยกสถานะ 2 ส่วน: สถานะเดินเครื่อง (`status` idle/running — ระบบผลิตตั้ง แก้ตรงไม่ได้) กับ **สภาพเครื่อง** (`condition`: ready / due / maintenance / retired + เหตุผล + ประวัติ) ที่เปลี่ยนผ่าน `POST /actions/machines/{id}/condition` เท่านั้น ต้องมีเหตุผลทุกครั้งที่ไม่ใช่ ready, ตั้ง maintenance/retired ไม่ได้ถ้ามีใบสั่งผลิตเปิดอยู่บนเครื่อง; `POST /actions/machines/{id}/maintenance` บันทึกซ่อม/PM (วันที่ไม่เกินวันนี้, ค่าใช้จ่าย, เวลาหยุด, ซ่อมเสร็จ → อัปเดตวันบำรุงล่าสุดและกลับเป็น ready); เปิด/ย้ายใบสั่งผลิตไปเครื่องที่ซ่อมอยู่/เลิกใช้/ไม่มีในทะเบียนถูกปฏิเสธ (ควรซ่อมบำรุงเลือกได้); PUT/PATCH คืนค่าฟิลด์ที่ server เป็นเจ้าของเสมอ; สิทธิ์ admin + ฝ่ายผลิต
- หน้าจอ (แท็บ "สถานะเครื่องจักร"): เพิ่มเครื่อง / แก้ไข / เปลี่ยนสภาพ (บังคับเหตุผล) / บันทึกซ่อมบำรุง / ประวัติ, แสดงระยะห่างเสา ช่วงความหนา รอบ PM (เลยกำหนด/ใกล้ครบ); ฟอร์มใบสั่งผลิตเลือกได้เฉพาะเครื่องที่ใช้ได้ + กล่องคำเตือนเมื่อคู่เครื่อง-แม่พิมพ์ไม่เข้ากัน (ตันนอกช่วง / กว้าง-ยาวเกินระยะห่างเสา (ลองสลับด้านแล้ว) / ความหนานอกช่วง) เปิดใบสั่งต่อได้; แจ้งเตือน (กระดิ่ง/แดชบอร์ด) เครื่องเลยรอบ PM/ใกล้ครบ/ควรซ่อมบำรุง/อยู่ระหว่างซ่อม; ปฏิทินซ่อมบำรุงรวมเครื่องจักร; แดชบอร์ดแสดงสภาพเครื่อง
- แม่พิมพ์: เพิ่มช่องขนาดแบบตัวเลข (กว้าง/ยาว/หนา) ในฟอร์มเพิ่มแม่พิมพ์; ข้อมูลตัวอย่างแปลงจากข้อความขนาดเดิมอัตโนมัติ
- ข้อมูลตัวอย่างเครื่อง: เพิ่มระยะห่างเสา/ช่วงความหนา/รอบ PM/วันบำรุงล่าสุด (ตัวเลขเป็นตัวอย่าง แก้ตามเครื่องจริง); INJ-06 เป็น "อยู่ระหว่างซ่อมบำรุง" (เฉพาะฐานข้อมูลที่ seed ใหม่)

**ผลทดสอบ:** gradlew test 55 เคสผ่าน (`MachineRulesTests` 8 เคส) + บนหน้าเว็บจริง: เพิ่ม INJ-07 (ตรวจกฎฝั่งหน้าจอ), เปลี่ยนสภาพ → ควรซ่อมบำรุง (ไม่ใส่เหตุผลถูกปฏิเสธ) → อยู่ระหว่างซ่อม (ตัดออกจากตัวเลือกเครื่องในใบสั่งผลิต) → บันทึกซ่อมเสร็จ (กลับพร้อมใช้งาน, ประวัติครบ 3 รายการ), ตั้งซ่อมเครื่องที่มีใบสั่งเปิดอยู่ถูกปฏิเสธ, INJ-06 + MLD-005 ขึ้น 2 คำเตือน
**ข้อจำกัด:** เครื่องเก่าในฐานข้อมูลที่ไม่ได้ seed ใหม่ไม่มีวันบำรุงล่าสุด/ระยะห่างเสา (แสดง "ยังไม่มีบันทึก" และไม่เตือน) ต้องกรอกที่ปุ่ม แก้ไข / บันทึกซ่อมบำรุง; เครื่องที่เคยเป็น `status: maintenance` แบบเก่าจะแสดงเป็นพร้อมใช้งานจนกว่าจะตั้งสภาพใหม่; รอบ PM นับเป็นวันเท่านั้น (ยังไม่ทำตามชั่วโมง/shot)

## 2026-11-17 · แจ้งเตือนและทางออกเมื่อวัตถุดิบไม่พอผลิต ✅ (ยังไม่ push / ไม่ deploy)
ผู้ใช้ชี้ว่าการปฏิเสธบันทึกผลิตเฉยๆ ไม่พอ ต้องรีบแจ้งให้เพิ่มสต๊อก — ทำข้อ 1–4 ตามที่อนุมัติ (เฉพาะหน้าจอ ไม่แตะ server)
- `Store.woShortage(wo)`: วัตถุดิบที่ขาดสำหรับจำนวนที่เหลือต้องผลิต + จำนวนชิ้นสูงสุดที่ผลิตได้ด้วยสต๊อกที่มี
- ช่องบันทึกผลิต: ตารางของที่ขาด (ต้องใช้/มีอยู่/ขาด), ผลิตได้สูงสุด X ชิ้น, ปุ่ม "สร้างใบสั่งซื้อวัตถุดิบที่ขาด", ปุ่ม "ผลิตเท่าที่ทำได้", แสดง PO ที่สั่งไว้แล้ว
- ป้าย "ขาดวัตถุดิบ" ใน Kanban และรายการใบสั่งผลิต
- กระดิ่งแจ้งเตือน + กล่อง "สิ่งที่ต้องดำเนินการ": ใบสั่งผลิตที่ขาดวัตถุดิบ (ระบุตัวที่ขาด จำนวน ผลิตได้สูงสุด และสั่งซื้อแล้วหรือยัง) ไปถึงทั้งฝ่ายผลิตและจัดซื้อ; หลังรับ PO ที่อ้างใบสั่งผลิตและของครบ ขึ้น "พร้อมผลิตแล้ว"
- ทดสอบบนหน้าเว็บจริง: ใบสั่งผลิต 100,000 ชิ้น ขาด PP 600 KG → ป้าย/แจ้งเตือน/ตารางถูกต้อง, สร้าง PO2026110007 (IRPC 600 KG @52) แล้วแจ้งเตือนเปลี่ยนเป็น "สั่งซื้อแล้ว", รับ PO แล้วขึ้น "พร้อมผลิตแล้ว" (หลังระบบดึงข้อมูลใหม่ ≤ 20 วินาที), "ผลิตเท่าที่ทำได้" 100,010 ชิ้นบันทึกสำเร็จที่ขอบเขตพอดี
- ข้อจำกัด: แจ้งเตือนแสดงในระบบเท่านั้น (ไม่ส่งอีเมล/ไลน์) — ผู้ใช้ยืนยันว่าพอ
- **หักการจองของใบสั่งผลิตอื่น แบบไม่มีลำดับสิทธิ์ (ผู้ใช้สั่ง "ต้องหัก" และ "ไม่ต้องให้ลำดับตามใบ เพื่อความยืดหยุ่นหน้างาน" — เลือกแบบ ข)**: ยอดขาดระดับวัตถุดิบ = ที่ทุกใบสั่งผลิตที่เปิดอยู่ (รอผลิต/ตั้งเครื่อง/กำลังผลิต) ต้องใช้รวมกัน (จำนวนที่เหลือต้องผลิต × ปริมาณต่อชิ้น) − สต๊อก − ที่สั่งซื้อไว้แล้วแต่ยังไม่รับ (PO รออนุมัติ/อนุมัติแล้ว); ทุกใบที่ใช้วัตถุดิบตัวนั้นและยังเหลือต้องผลิตเห็นยอดขายรวมเดียวกัน; ปุ่มสร้าง PO จากของขาด (ทั้งช่องบันทึกผลิตและการ์ดจอง) สั่งตามยอดขายรวมนี้ใน PO ใบเดียว (เก็บใบสั่งผลิตที่เกี่ยวข้องไว้ใน `forWo`) แล้วไม่เตือน/สั่งซ้ำ; ของที่มี PO รองรับแต่ยังไม่รับขึ้น "รอรับวัตถุดิบ" (สีเหลือง) แทน "ขาดวัตถุดิบ"; ใบที่ผลิตครบ (เหลือ 0) ไม่ถูกเตือน
- "ผลิตได้สูงสุด" ดูจากสต๊อกจริงที่มี (ไม่หักของใบอื่น) และการจองไม่บล็อกการผลิต — server ปฏิเสธเฉพาะเมื่อสต๊อกจริงไม่พอ
- ทดสอบบนหน้าเว็บจริง: สต๊อก PP 1,000 กก. ใบ 04 ต้อง 1,821.6 ใบ 05 ต้อง 1,821.4 → ทั้งสองใบเห็นขาดรวม 2,643; สร้าง PO2026110008 (2,644 กก.) ใบเดียว → ทั้งสองใบเปลี่ยนเป็น "รอรับวัตถุดิบ" และปุ่มสั่งซื้อถูกปิด (ไม่สั่งซ้ำ); รับ PO แล้วขึ้น "พร้อมผลิตแล้ว" สำหรับใบที่ยังไม่เริ่มผลิต

## 2026-11-17 · BOM หลายสูตรต่อสินค้า (ขั้นที่ 1) + ตัดวัตถุดิบตอนผลิตที่ server ✅ (ยังไม่ push / ไม่ deploy)
อนุมัติโดยผู้ใช้ — สินค้าหนึ่งรหัสมีได้หลายสูตร (เม็ดคนละเบอร์ / สีต่างกัน), มาสเตอร์แบตช์เป็น % ของเม็ดได้, เศษรีไซเคิลเป็นทางเลือก; ขั้นที่ 2 (ปรับสัดส่วนต่อใบสั่ง, ตารางเทียบสูตร) ยังไม่ทำ

**ปัญหาเดิม:** BOM ฝังเป็นค่าตายตัวในโค้ด ไม่มีหน้าสร้าง/แก้, และการตัดวัตถุดิบตอนบันทึกผลิตทำฝั่งเบราว์เซอร์ (ซิงก์ทีละ record, stock ติดลบได้เงียบๆ)

**สิ่งที่เปลี่ยน**
- Server (`BomService` ใหม่ + `RecordService`): collection `boms` เก็บสูตร (ชื่อ, สี, สถานะ draft/active/inactive, สูตรหลัก, revision, % เผื่อเสีย, รายการ) ชนิดบรรทัด resin / masterbatch / additive / regrind กำหนดเป็น กก./ชิ้น หรือ % ของเม็ด; กฎ: สินค้าและวัตถุดิบต้องมี/ใช้งาน, ปริมาณ > 0, ไม่ซ้ำ, ต้องมีเม็ดอย่างน้อย 1 รายการ, % อยู่ใน (0,100), ห้ามลบ (ใช้เลิกใช้), เปลี่ยนสินค้าของสูตรไม่ได้, เลิกใช้/แก้เป็นร่างไม่ได้ถ้ามีใบสั่งผลิตที่เปิดอยู่อ้างอิง; revision/updatedBy/สูตรหลักเป็นของ server (สูตรใช้งานแรกเป็นสูตรหลักอัตโนมัติ, ตั้งสูตรใหม่เป็นหลักแล้วสูตรอื่นถูกปลด)
- ใบสั่งผลิต: เลือกสูตรตอนเปิด (ไม่เลือก = สูตรหลัก) server สร้าง `bomSnapshot` (ปริมาณ กก./ชิ้น ที่แปลงจาก % แล้ว) เอง แก้ BOM ภายหลังไม่กระทบใบเดิม; client แก้ bomId/snapshot ไม่ได้ (server คืนค่าเดิมเงียบๆ เพื่อไม่ขวาง sync)
- `WorkflowService.produceWO`: ตัดวัตถุดิบตาม snapshot (ใบเก่าที่ไม่มี snapshot ใช้สูตรหลักปัจจุบัน) ล็อกวัตถุดิบเรียงตามรหัส; วัตถุดิบไม่พอ = ปฏิเสธทั้งหมด (422 บอกว่าตัวไหนขาด) ไม่ตัดสต๊อก/ไม่บันทึกผลิตเลย **(เปลี่ยนพฤติกรรม: เดิมปล่อยให้ติดลบ)**
- หน้าจอ: `Store.produceWO` เรียก API; หน้า "สต๊อก / BOM" เป็นหน้าจัดการ (สร้าง/แก้/คัดลอก/ตั้งสูตรหลัก/เลิกใช้, ตัวอย่างต้นทุนสดตอนกรอก); ฟอร์มเปิดใบสั่งผลิตเลือกสูตรพร้อมต้นทุนต่อชิ้นและความพอของวัตถุดิบ; หน้าวัตถุดิบมี "ใช้ใน BOM"; ตัดการประเมินสูตรสำรอง (`_RESIN_FALLBACK`) ออก; ข้อมูลตัวอย่าง BOM ย้ายเป็น seed ของฐานข้อมูลใหม่

**ผลทดสอบ:** gradlew test 47 เคสผ่าน (`BomRulesTests` 9 เคส: กฎ, สูตรหลัก/revision, % → กก./ชิ้น, เลือกสูตรและ snapshot, ตัดสต๊อก, rollback เมื่อไม่พอ, ผลิตพร้อมกัน 6 ใบเหลือผลิตได้ 1) + ทดสอบบนหน้าเว็บจริงในเครื่อง: สร้างสูตร, คัดลอกเป็นสูตรที่สอง (3%), เปิดใบสั่งผลิตเลือกสูตร, บันทึกผลิต 1,000 ชิ้น (PP −18.216, มาสเตอร์ −0.546, สินค้า +990 ตรงสูตร)
**ยังไม่ได้ทดสอบบนหน้าจอ:** ข้อความตอนวัตถุดิบไม่พอ (ปุ่มถูกปิดฝั่งหน้าจอ), สิทธิ์ฝ่ายผลิต/จัดซื้อในหน้า BOM, เส้นทาง seed ฐานข้อมูลว่างบน UAT

## 2026-11-17 · ราคาวัตถุดิบเกิดจาก PO เท่านั้น (เลิกกรอกราคาตอนสร้าง/แก้วัตถุดิบ) ✅ (ยังไม่ push / ไม่ deploy)
อนุมัติโดยผู้ใช้ — ราคาขึ้นลงตลอด จึงกรอกที่ PO แล้วระบบคำนวณต้นทุนเอง; ข้อมูลใน ERP ตอนนี้เป็นข้อมูลทดลอง

**สิ่งที่เปลี่ยน**
- Server: PUT/PATCH เปลี่ยน `cost` / `costHistory` ไม่ได้ทุก role (409 `COST_MANAGED`) ส่งค่าเดิมซ้ำได้; วัตถุดิบใหม่ ส่ง `cost` = ต้นทุนยกมา (ไม่ติดลบ) และ server สร้าง `costHistory` เอง; `POST /actions/materials/{id}/adjust-cost` เฉพาะ admin ต้องมีเหตุผล บันทึกประวัติ (ref MANUAL) + audit
- หน้าวัตถุดิบ: ตัดช่องราคาทุนออก; มีช่อง "ต้นทุนยกมา" เมื่อกรอกยอดยกมา > 0 (บังคับ); ตอนแก้ไขแสดงต้นทุนอย่างเดียว + ปุ่ม "ปรับต้นทุน" สำหรับ admin; รายการแสดง "ยังไม่มีต้นทุน" เมื่อเป็น 0
- ฟอร์ม PO: ราคาตั้งต้นเป็นราคาซื้อล่าสุด (ไม่เคยซื้อ = ว่าง)
- สร้าง PO จากของขาด: ใช้ราคาซื้อล่าสุด/ต้นทุนถัวเฉลี่ย ถ้าไม่มีราคาเลยหรือจับคู่ Supplier ไม่ได้ จะแจ้งข้อความชัดเจนและไม่สร้าง (เดิมถูก server ปฏิเสธเงียบ ๆ ตามกฎ PO)
- ต้นทุนประเมิน BOM แสดง "ยังไม่มีต้นทุน" เมื่อ cost เป็น 0
- (เพิ่มหลังทดสอบ UAT ในเครื่อง) หน้าแก้ไขวัตถุดิบมีกล่อง "ประวัติต้นทุน" แสดงทุกครั้งที่ต้นทุนเปลี่ยน (ยกมา / ถัวเฉลี่ยจาก PO / admin ปรับ) พร้อมไฮไลต์การปรับด้วยมือ กัน admin ลืมว่าเคยปรับ

**ผลทดสอบ:** gradlew test 38 เคสผ่าน (เพิ่ม: แก้ cost ตรงถูกปฏิเสธทุก role, adjust-cost เฉพาะ admin/ต้องมีเหตุผล/บันทึกประวัติและ audit, วัตถุดิบใหม่ cost 0 แล้วรับ PO แรก = ราคา PO, ต้นทุนยกมา)
**ยังไม่ได้ทดสอบ:** หน้าจอจริง (ฟอร์มวัตถุดิบ, modal ปรับต้นทุน, ปุ่มสร้าง PO จากของขาด)

## 2026-11-17 · Material Costing: ต้นทุนถัวเฉลี่ยเคลื่อนที่ + ประวัติราคาซื้อ ✅ (ยังไม่ push / ไม่ deploy)
อนุมัติขอบเขตโดยผู้ใช้ — ยังไม่ทำ FIFO / Stock Card เต็มรูปแบบ (รอ B5) และไม่แตะต้นทุนสินค้าสำเร็จรูป

**ปัญหา:** ซื้อวัตถุดิบราคาไม่เท่ากันแต่ตอนรับ PO ระบบไม่อัปเดต `cost` และ movement ไม่เก็บราคา

**สิ่งที่เปลี่ยน**
- `WorkflowService.receivePO`: คำนวณ Moving Average ใน transaction เดียวกับการเพิ่ม stock — ต้นทุนใหม่ = (stock เดิม × cost เดิม + qty × ราคา PO ก่อน VAT) ÷ (stock เดิม + qty), ปัด 4 ตำแหน่ง; stock เดิม ≤ 0 ใช้ราคา PO; บรรทัดที่ไม่มีราคาไม่เปลี่ยนต้นทุน
- movement ขารับเพิ่ม `unitCost`, `value`, `costBefore`, `costAfter`; `costHistory` ของ Material เพิ่มรายการอ้างเลข PO
- `page-inventory.jsx`: ฟอร์มแก้วัตถุดิบแสดงประวัติราคาซื้อ (ล่าสุด/เฉลี่ยถ่วงน้ำหนัก/ต่ำสุด–สูงสุด + รายการล่าสุด) จาก PO ที่รับแล้ว
- `page-procurement.jsx`: ฟอร์ม PO แสดงราคาซื้อล่าสุด/ช่วงราคา/ต้นทุนถัวเฉลี่ย และ % ต่างจากราคาล่าสุด
- ปรับสต๊อกด้วยมือและตัดวัตถุดิบตอนผลิตไม่เปลี่ยน `cost`; แก้ `cost` ด้วยมือยังทำได้เฉพาะ admin/procurement

**ผลทดสอบ:** gradlew test 36 เคสผ่านทั้งหมด (`MaterialCostingTests` 10 เคส: 100@50 + 100@56 = 53.00, ราคาลง, ต่อเนื่องหลายครั้ง, stock 0/ติดลบ, รับซ้ำไม่คำนวณซ้ำ, rollback ไม่เปลี่ยนต้นทุน, รับพร้อมกัน 10 PO ได้ผลเท่ารับต่อเนื่อง)
**ยังไม่ได้ทดสอบ:** หน้าจอจริง (UI ประวัติราคา/ข้อความในฟอร์ม PO)
**ผลกระทบ:** มูลค่าสต๊อก ต้นทุนประเมิน BOM และ analytics จะขยับตามราคาซื้อจริงหลังรับของ

## 2026-11-17 · Purchase Order Management + PO Receiving → Stock ✅ (ยังไม่ push / ไม่ deploy)
อนุมัติขอบเขตโดยผู้ใช้ — ไม่ทำรับบางส่วน/GR เต็มรูปแบบ ไม่เปลี่ยนสถาปัตยกรรม

**สาเหตุที่ stock ไม่เพิ่ม (จาก audit):** ปุ่มรับของเรียก `Store.receivePO` ฝั่งเบราว์เซอร์ แล้วซิงก์ขึ้น server ทีละ record (ไม่อยู่ใน transaction เดียว) ขณะที่ `WorkflowService.receivePO` ฝั่ง server ไม่เคยถูกเรียก, บรรทัดที่จับคู่วัตถุดิบไม่ได้ถูกข้ามเงียบ ๆ แต่ PO ยังถูกเปลี่ยนเป็น received

**สิ่งที่เปลี่ยน**
- `RecordService`: กฎ PO ฝั่ง server — Supplier ต้องมีและ active, ทุกบรรทัดต้องเลือกวัตถุดิบจากทะเบียน (ไม่ซ้ำ, qty/price > 0), server คำนวณ subtotal/VAT 7%/total เอง, สร้างได้เฉพาะ draft/pending, ลำดับสถานะ, ตั้งสถานะ received ตรง ๆ ไม่ได้, อนุมัติแล้วแก้รายการ/ยอดไม่ได้, ยกเลิกต้องมีเหตุผล, PO ที่ received/cancelled ล็อก, ลบ PO ที่ approved/received ไม่ได้, ประทับผู้อนุมัติ/เวลาโดย server
- `WorkflowService.receivePO`: จับคู่วัตถุดิบครบทุกบรรทัดก่อน บรรทัดใดจับคู่ไม่ได้ (หรือ qty <= 0 / ไม่มีรายการ) ปฏิเสธทั้งใบ แล้วค่อยเพิ่มสต๊อก + movement (ref = เลข PO) + เปลี่ยนสถานะ + ตั้งเจ้าหนี้ ใน transaction เดียว
- `store.jsx` / `page-procurement.jsx`: ปุ่มรับของเรียก `POST /actions/purchase-orders/{id}/receive` (รอให้การอนุมัติที่ค้างซิงก์ก่อน แล้วโหลดข้อมูลใหม่), กันกดซ้ำ, ฟอร์ม PO ไม่ให้ส่งบรรทัดพิมพ์เอง
- Tests: `PurchaseOrderRulesTests` (9 เคส) + ปรับ `ErpApplicationTests`/`SupplierRulesTests` ให้ใช้ PO ที่ถูกต้องตามกฎใหม่

**ผลทดสอบ:** gradlew test — 26 เคสผ่านทั้งหมด (รวมรับของพร้อมกัน 8 request เพิ่มสต๊อกครั้งเดียว, rollback เมื่อบรรทัดจับคู่ไม่ได้, รับซ้ำ/ยกเลิก/ยังไม่อนุมัติ/ไม่มีสิทธิ์ถูกปฏิเสธ)
**ยังไม่ได้ทดสอบ:** กดปุ่มในหน้าเว็บจริง (UI) — ต้องทดสอบบน UAT หลัง deploy
**ข้อควรรู้:** PO เก่าที่มีบรรทัดพิมพ์เอง/จับคู่วัตถุดิบไม่ได้ จะรับของไม่ได้ ต้องยกเลิกแล้วออกใหม่

- **เปรียบเทียบสูตร**: ปุ่มที่หัวกลุ่มสินค้าในหน้า BOM เลือก 2–3 สูตร ดูปริมาณ/เผื่อเสีย/ต้นทุนต่อชิ้นและส่วนต่างจากสูตรแรก (ฝั่งหน้าจออย่างเดียว)
