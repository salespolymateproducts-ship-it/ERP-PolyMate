## 2. D-1 ที่ตั้ง Server — **เลือก Cloud แล้ว (รายละเอียดดู [Cloud-Infrastructure](Cloud-Infrastructure.md)) · ส่วนด้านล่างเก็บไว้เป็นบันทึกการพิจารณา**

### 2.1 ทางเลือก

| | (ก) เครื่องในโรงงาน (On-premise) | (ข) Cloud VPS (ไทย/สิงคโปร์) | (ค) ผสม: Cloud เป็นหลัก + สำเนาสำรองที่ NAS โรงงาน |
|---|---|---|---|
| ข้อมูลอยู่ที่ | บริษัท | ผู้ให้บริการ | ผู้ให้บริการ + สำเนาที่บริษัท |
| ใช้งานนอกโรงงาน (ฝ่ายขายนอกสถานที่, ผู้บริหาร) | ต้องตั้ง VPN หรือ Cloudflare Tunnel | ได้ทันที | ได้ทันที |
| เน็ตโรงงานล่ม | **คนในโรงงานยังใช้ได้** คนนอกใช้ไม่ได้ | **คนในโรงงานใช้ไม่ได้** | คนในโรงงานใช้ไม่ได้ |
| ไฟดับ | ต้องมี UPS + เครื่องเปิดเองหลังไฟมา | ไม่กระทบ server | ไม่กระทบ server |
| เครื่องเสีย | กู้จาก backup ลงเครื่องใหม่ (RTO ~2 ชม. ถ้ามีเครื่องสำรอง) | ผู้ให้บริการดูแล hardware | เหมือน (ข) |
| ผู้ดูแล | ต้องมีคนดูเครื่อง/ดิสก์/อัปเดต OS | ดูแลน้อยกว่า | เหมือน (ข) + ดู NAS |
| ค่าใช้จ่าย (ประมาณการ ต้องเช็คราคาจริงอีกครั้ง) | ครั้งเดียว: เครื่อง ~25,000–40,000 + UPS ~5,000 บาท | ~600–1,500 บาท/เดือน (2 vCPU, 4 GB RAM) | (ข) + NAS ถ้ายังไม่มี |
| PDPA / ความลับข้อมูล | ควบคุมเองทั้งหมด | ขึ้นกับผู้ให้บริการ (เลือกศูนย์ข้อมูลในไทยได้) | เหมือน (ข) |
| ขยายในอนาคต (หลายสาขา, ลูกค้า/Supplier เข้าระบบ) | ทำได้แต่ต้องเปิดเครื่องออกอินเทอร์เน็ต | ง่ายที่สุด | ง่าย |

**ผลต่อ 4 มุม:** โต: (ข)/(ค) ขยายง่ายกว่า · ขาย/บัญชี/ย้อนหลัง: **ไม่ต่างกัน** เพราะโค้ดและฐานข้อมูลเหมือนกันทุกทางเลือก (Docker Compose ชุดเดียว ย้ายเครื่องได้ด้วย backup + restore)

### 2.2 คำถามที่ต้องตอบก่อนเลือก
1. จะมีผู้ใช้กี่คน และใช้พร้อมกันสูงสุดกี่คน
2. ต้องใช้ระบบนอกโรงงานหรือไม่ (ฝ่ายขาย, ผู้บริหาร, ทำงานจากบ้าน)
3. อินเทอร์เน็ตโรงงานล่มบ่อยแค่ไหน และมีสายสำรองหรือไม่
4. มีเครื่อง server/NAS/UPS อยู่แล้วหรือไม่ และมีคนดูแล IT ในบริษัทหรือไม่
5. มีข้อกำหนดของลูกค้า (เช่นลูกค้ากลุ่ม Medical/Automotive) เรื่องที่เก็บข้อมูลหรือไม่

**แนวทางตัดสิน:** ถ้าข้อ 2 = ใช่ และไม่มีคนดูแล IT → (ค) · ถ้าทุกคนอยู่ในโรงงานและเน็ตไม่เสถียร → (ก) + UPS + backup นอกเครื่อง

### 2.3 ผลต่อแผนงาน
D-1 **ไม่ส่งผลต่อโค้ดใน B2** (พัฒนาและทดสอบบน Docker ในเครื่องนี้) แต่ต้องตัดสินก่อน B3 (ต้องมีเครื่อง staging ให้ผู้ใช้ทดลองย้ายข้อมูลจริง) ตามที่คุณกำหนดไว้ B2 จะเริ่มหลังอนุมัติครบทุกข้อ ถ้าต้องการเริ่ม B2 ระหว่างหาข้อมูล D-1 แจ้งได้

## 3. D-2 ถึง D-10

### D-2 วิธี Login → แนะนำ: **Session ใน Database + Cookie (HttpOnly) + CSRF token**
- **ทางเลือกอื่น:** JWT (token ที่เบราว์เซอร์ถือไว้เอง)
- **โต:** รองรับผู้ใช้หลักร้อยคนสบาย ถ้าในอนาคตต้องมี Mobile App ค่อยเพิ่ม token เฉพาะแอปได้
- **ขาย/บัญชี:** ไม่กระทบ
- **ย้อนหลัง:** ระงับบัญชีพนักงานที่ลาออกแล้ว **มีผลทันที** (JWT จะใช้ได้ต่อจนกว่าหมดอายุ)
- **ความเสี่ยงที่เหลือ:** ต้องทำ CSRF ให้ถูก (มี test ใน B2)
- **ย้อนกลับ:** 🟢 ง่าย

### D-3 ชั้นเข้าถึงฐานข้อมูล → แนะนำ: **Kysely**
- **ทางเลือกอื่น:** Prisma (เขียนง่ายกว่า), SQL ล้วน
- **บัญชี:** การตัดสต๊อก/ต้นทุน FIFO ต้อง "ล็อกแถว" (`SELECT … FOR UPDATE`) ตอนคนสองคนตัดสินค้าตัวเดียวกันพร้อมกัน Kysely เขียนได้ตรง Prisma ทำได้แต่ต้องอ้อม
- **โต:** query รายงานซับซ้อน (อายุลูกหนี้, Stock card) เขียน SQL ที่มี index รองรับได้เต็มที่
- **ย้อนกลับ:** 🟠 ต้องเขียนชั้น repository ใหม่ แต่ไม่กระทบ schema/ข้อมูล

### D-4 วิธีเชื่อมหน้าจอเดิมกับ Backend → แนะนำ: **Store Adapter (หน้าจอเดิม + เปลี่ยนแค่ชั้นข้อมูล)**
- **ทางเลือกอื่น:** เขียนหน้าจอใหม่ด้วย React Query
- **ขาย:** ✅ ตรงข้อกำหนด "ห้ามเปลี่ยน UI / ห้ามทำ workflow เดิมเสีย" — ฟังก์ชันที่หน้าจอเรียก (`Workflow.approve`, `convert` …) ชื่อและพารามิเตอร์เดิม มี test เดิม 50 กรณีคุม และมีสวิตช์กลับไปโหมด localStorage ระหว่าง B3
- **โต:** เบราว์เซอร์เก็บเฉพาะข้อมูลหลัก + เอกสารที่เปิดอยู่ + 90 วันล่าสุด ประวัติเก่าโหลดแบบแบ่งหน้า รองรับข้อมูลหลายปีได้ ถ้าวันหนึ่งข้อมูลเปิดค้างเยอะมาก ปรับเป็นหน้าละชุดทีละหน้าได้ ไม่ต้องรื้อทั้งระบบ
- **ความเสี่ยงที่เหลือ:** ผู้ใช้อื่นเห็นข้อมูลใหม่ช้าสุด 15 วินาที (แต่ server ตรวจคงเหลือจริงทุกครั้ง จึงไม่เกิดออกเอกสารเกิน)
- **ย้อนกลับ:** 🟠 เปลี่ยนเป็นแบบอื่นทีละหน้าได้

### D-5 โครงสร้างตารางเอกสาร → แนะนำ: **ตารางกลาง `documents` + `document_lines` + `document_links` สำหรับทุกประเภท** 🔴
- **ทางเลือกอื่น:** แยกตารางต่อประเภท (quotations, invoices, purchase_orders …)
- **ขาย:** engine เดิมเป็นแบบนี้อยู่แล้ว (เอกสารทุกประเภทอยู่ใน `docs` เดียว อ้างอิงกันระดับรายการ) จึงย้ายได้ตรงตัว ลดความเสี่ยงทำ workflow เดิมเสีย
- **บัญชี/จัดซื้อ:** PO, GR, ใบแจ้งหนี้ผู้ขาย, CN/DN/คืนสินค้า ใช้ engine เดียวกับฝ่ายขาย ได้ อนุมัติ/ยกเลิก/ประวัติ/คงเหลือ/กันเกินจำนวน ครบทันทีโดยไม่เขียนซ้ำ
- **ย้อนหลัง:** กฎยกเลิก ("มีเอกสารปลายทางห้ามยกเลิก", "ยกเลิกแล้วคืนยอดต้นทาง") เขียนครั้งเดียวใช้ทุกประเภท
- **โต:** ค้นหาเอกสารทุกประเภทจากที่เดียว; ถ้าข้อมูลเกินหลายล้านแถวแบ่ง partition ตามปีได้ · ฟิลด์เฉพาะประเภทอยู่ตารางเสริม (`payments`, `shipments`, `ar_items`) ไม่ยัดในตารางกลาง
- **ข้อเสีย:** ตารางกลางต้องมี index ดี และต้องระวังไม่ให้ใส่ข้อมูลเฉพาะประเภทลง JSON มากเกิน (กำหนดกติกา: field ที่ใช้ค้นหา/คำนวณต้องเป็นคอลัมน์จริงเสมอ)
- **ย้อนกลับ:** 🔴 ยากมาก

### D-6 เวลาออกเลขที่เอกสาร → แนะนำ: **ออกเลขจริงเมื่ออนุมัติ (ฉบับร่างใช้เลขชั่วคราว) ยกเว้น QT, CPO, PR, PO ออกเลขตอนสร้าง** 🔴
- **ทางเลือกอื่น:** ออกเลขตอนสร้างร่างทุกประเภท (แบบเดิม)
- **ย้อนหลัง/บัญชี:** ใบกำกับภาษีและใบเสร็จเรียงเลขต่อเนื่องไม่มีช่องว่างจากการลบร่าง (เลขที่ยกเลิกหลังอนุมัติยังอยู่ในระบบพร้อมเหตุผล ตรวจย้อนหลังได้และไม่ถูกนำกลับมาใช้)
- **ขาย:** สิ่งที่เปลี่ยนจากเดิม: ร่าง SO/DO/BN/INV/RC จะแสดง `DRAFT-…` แทนเลขจริงจนกว่าจะอนุมัติ ส่วน QT ที่ต้องส่งลูกค้าก่อนยังได้เลขจริงตั้งแต่สร้าง (ตั้งค่าต่อประเภทได้ในตาราง `doc_types`) · เอกสารเดิมที่ย้ายมาคงเลขเดิมทุกใบ
- **โต:** ตั้งรูปแบบเลขต่อประเภทได้ (เช่นแยกเล่มต่อสาขาในอนาคต)
- **คำถามถึงคุณ:** ปัจจุบันฝ่ายขายส่งเลข SO/DO ให้ลูกค้าก่อนอนุมัติหรือไม่ ถ้าใช่ จะเพิ่ม SO/DO ในกลุ่ม "ออกเลขตอนสร้าง"
- **ย้อนกลับ:** 🔴 เลขที่ออกไปแล้วแก้ไม่ได้

### D-7 ระดับวิธีคิดต้นทุน → แนะนำ: **ระดับบริษัท (ทุกคลังใช้วิธีเดียว) โครงสร้างรองรับระดับคลังไว้แล้ว** 🔴
- **ทางเลือกอื่น:** เลือกวิธีต่อคลังตั้งแต่แรก
- **บัญชี:** มาตรฐานการบัญชี (TAS 2) ให้ใช้วิธีเดียวกันกับสินค้าลักษณะเดียวกัน ผู้สอบบัญชีตรวจง่าย · **วิธี (FIFO หรือ Moving Average) ยังไม่ต้องเลือกตอนนี้** เลือกใน B5 หลังเห็นตัวเลขทดสอบ
- **ย้อนหลัง:** เปลี่ยนวิธีได้เฉพาะวันแรกของงวด ผ่านเอกสารที่ต้องอนุมัติ ต้นทุนของเอกสารที่ลงบัญชีแล้วไม่ถูกแก้ · รายการย้อนหลังในงวดที่ปิดแล้วถูกปฏิเสธ
- **โต:** เปิดคลังใหม่/สาขาใหม่ได้ ถ้าวันหนึ่งต้องแยกวิธีต่อคลัง ตาราง `costing_policies` มีคอลัมน์ `warehouse_id` รองรับแล้ว
- **ย้อนกลับ:** 🔴 (การเปลี่ยนวิธีมีขั้นตอนรองรับ แต่กระทบตัวเลขงบการเงิน)

### D-8 สำเนา Backup นอกเครื่อง → แนะนำ: **ทั้ง NAS ในบริษัท และ Cloud storage (เข้ารหัสก่อนส่ง)**
- **ทางเลือกอื่น:** อย่างใดอย่างหนึ่ง
- **ย้อนหลัง/บัญชี:** ป้องกันทั้งเครื่องเสีย, ไฟไหม้/น้ำท่วม, ransomware (สำเนา cloud แบบแก้ไขย้อนหลังไม่ได้)
- **ค่าใช้จ่าย:** ข้อมูลระดับนี้ใช้พื้นที่ cloud ไม่กี่ GB/ปี (หลักสิบถึงร้อยบาท/เดือน, ต้องเช็คราคาผู้ให้บริการ)
- **ย้อนกลับ:** 🟢 ง่าย

### D-9 บัญชีแยกประเภท (GL / สมุดรายวันคู่) → แนะนำ: **ยังไม่ทำในรอบนี้ แต่ออกแบบให้สร้างภายหลังได้ (เสนอเป็น Phase B8)**
- **ทางเลือกอื่น:** ทำ GL เต็มรูปใน B6
- **บัญชี (ต้องรู้ก่อนอนุมัติ):** ระบบจะมีลูกหนี้, เจ้าหนี้, สต๊อก+ต้นทุน, ภาษีขาย/ซื้อ, 50 ทวิ, P&L ระดับบริหาร **แต่ยังไม่มีผังบัญชี/สมุดรายวัน/งบทดลอง/งบดุล** ฝ่ายบัญชีหรือสำนักงานบัญชียังต้องลงบัญชีในโปรแกรมบัญชีเดิม (ระบบส่งออกรายงานให้)
- **ย้อนหลัง:** ข้อมูลทุกรายการใน sub-ledger ไม่ถูกแก้/ลบ และอ้างเอกสารต้นทาง จึงสร้างรายการบัญชีย้อนหลังได้เมื่อทำ B8
- **โต:** เมื่อบริษัทต้องการปิดงบในระบบเดียว ทำ B8 เพิ่ม (ประมาณ 3–4 สัปดาห์) โดยไม่ต้องรื้อของเดิม
- **ย้อนกลับ:** 🟢 เพิ่มทีหลังได้

### D-10 ภาษาโปรแกรม Backend → แนะนำ: **TypeScript**
- **ทางเลือกอื่น:** JavaScript (แบบเดียวกับหน้าจอเดิม)
- **โต/บัญชี:** ระบบจะมีราว 60 ตาราง ชนิดข้อมูลช่วยจับข้อผิดพลาด เช่น ส่งจำนวนแทนราคา หรือลืมฟิลด์ ตั้งแต่ตอนเขียน ไม่ใช่ตอนตัวเลขผิดในรายงาน
- **ขาย:** หน้าจอเดิมยังเป็น JavaScript เหมือนเดิม
- **ย้อนกลับ:** 🟠 ต้องเขียนใหม่ทั้ง backend (ไม่มีเหตุให้ต้องย้อน)
